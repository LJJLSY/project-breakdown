## 1. 这个项目是什么

MetaNode 是一个**链下撮合、链上结算**的去中心化永续合约交易系统（教学项目），三层结构：

```
┌─────────────┐   ┌──────────────────────────────┐   ┌──────────────────────────┐
│  前端 fe/    │   │         后端 backend/         │   │        链上 src/          │
│ Next.js     │   │ Go (go-zero)                  │   │ Solidity (Foundry)        │
│             │   │                              │   │                          │
│ EIP-712 签名│──▶│ 订单 API → 内存订单簿撮合       │   │                          │
│ 下单/持仓展示│   │ 扫链入库 → Supabase/Redis      │──▶│ Perpetual.trade()        │
│             │   │ 撮合成功 → 用 orderSender      │   │ MetaNodeDealer 保证金/清算 │
│             │◀──│ 私钥发交易上链                 │◀──│ 资金费率 / 预言机           │
└─────────────┘   └──────────────────────────────┘   └──────────────────────────┘
```

一句话流程：**用户签名订单（免 gas）→ 后端撮合（毫秒级）→ 只有成交才上链结算（安全）**。

学完这个仓库，你应该能回答三个问题：

1. 为什么订单簿放链下、结算放链上？（延迟、gas、吞吐的权衡）
2. 一笔成交从签名到仓位变化，数据在前后端和链上各经历了什么？
3. 资金费率、保证金、清算这些"金融规则"是如何用数据结构（而非数据库表）表达的？

### 2.1 架构全景速览（读代码前先看图）

**链上（src/）—— 两个核心合约 + 拆分继承 + 市场/预言机：**

```
MetaNodeDealer（唯一部署的交易台合约，按职责拆 4 个文件、一条继承链共享存储）
 ├─ MetaNodeExternal    用户/Perpetual 入口：deposit、withdraw、approveTrade、
 │                      requestLiquidation、openPosition、realizePnl
 ├─ MetaNodeOperation   Owner/Keeper 配置：updateFundingRate、setPerpRiskParams、
 │                      setOrderSender……
 ├─ MetaNodeView        只读查询：getTraderRisk、isSafe、getLiquidationPrice、
 │                      getCreditOf……
 └─ 共同继承 MetaNodeStorage（全部状态打包在 Types.State state 一个 struct + domainSeparator）
       │ owner
       ├─ Perpetual ×N（每市场一个）— balanceMap{paper, reducedCredit}、fundingRate
       │    └─ RiskParams.markPriceSource → OracleAdaptor(Chainlink) / Pyth / Const / Emergency
       └─ SubaccountFactory ── EIP-1167 Clones ──▶ Subaccount ×N（execute 任意转发）
```

**两条权限主线**（互相咬合的安全设计）：只有"已注册的 Perpetual"能改 Dealer 状态（`onlyRegisteredPerp`）；只有 Dealer（owner）能改 Perpetual 的 fundingRate 并验证 trade。任何外部地址都绕不开这两条线。

**交易主链路**（务必自己跟一遍代码）：

```
撮合引擎(orderSender) → Perpetual.trade(tradeData)
  → Dealer.approveTrade：校验 orderSender → abi.decode(Order[],签名[],成交量[])
       → ECDSA.tryRecover 验签（或 ERC-1271）→ 过期/自成交/累计成交量校验
       → Trading._matchOrders：以 maker 价撮合 → 双方变化 + 手续费
            （手续费归撮合引擎；为负时检查引擎自身 IM 安全）
  ← 返回变化数组 → Perpetual._settle 逐交易者记账
       （新开仓 → Dealer.openPosition；全平 → Dealer.realizePnl）
  → Dealer.isAllSafe（全部 MM 兜底检查，不通过整体回滚）
```

**另两条链**：

- **清算**：任何人 → `Perpetual.liquidate` → `Dealer.requestLiquidation`（固定折扣定价 + 保险费入保险账户）→ `_settle` 双方 → 价格保护 → 穿仓时 `handleBadDebt`（负余额转保险账户兜底）
- **资金费**：fundingRateKeeper → `Dealer.updateFundingRate`（批量）→ 各 Perpetual 改一个全局 `fundingRate` → 所有持仓者 credit **隐式**变化（O(1) 批量结算，无需逐账户转账）

**链下（others/backend/）—— 常驻 Go 进程，启动时装配多个后台任务：**

```
metanode.go 装配：
  TreasuryDepositWatcher   12s 轮询扫链充值 → deposits/ledger 台账（Redis 游标 + 幂等唯一约束）
  CompositeSpotIndex       Coinbase:OKX:Binance WebSocket 加权指数价（4:3:3）
  MatchEngine              内存订单簿撮合 + 批量上链 + WAL 事件回放恢复 + Redis leader 锁
  FundingRateKeeper        8 小时资金费结算（链下算费率，链上 updateFundingRate）
  Liquidator               清算机器人（当前占位未实现）
  HTTP :28888              REST API + WS 行情推送
```

**数据来源三方式**：① 实时 `eth_call` 查链（仓位/风险/标记价，不落库）② 扫链入库（**只有充值走扫链**）③ 引擎自己产生（订单/成交/资金费历史落库）。详见 [后端数据流：扫链-入库-API](../others/backend/docs/后端数据流：扫链-入库-API.md)。

## 3. 核心概念速览（先建立直觉，再读代码）

学习代码前，先用 30 分钟把下面 5 个概念弄懂，详细推导在 [docs/1.md](./1.md)（业务基础，Go/Solidity 双语示例）：

### 3.1 仓位 = paper + credit（资产负债表的双字段模型）

- `paper`：持仓数量（BTC 数量），做多为正、做空为负
- `credit`：美元计价的"欠款"，可正可负
- 例：$30,000 做多 1 BTC → `paper=1, credit=-30000`；做空 → `paper=-1, credit=30000`
- **永续合约的一切状态变化只有三种**：资金费率、交易、清算
- 详见 [others/docs/Position_Storage_And_Trading.md](../others/docs/Position_Storage_And_Trading.md)

### 3.2 资金费率 = 让合约价锚定现货价的机制

- 合约价 > 现货价 → 多头付空头；反之空头付多头（每 8 小时结算一次）
- 实现用**累计值**而非定期转账：`credit = paper × fundingRate + reducedCredit`
- 更新一次 `fundingRate` 全局变量 = 对所有持仓者按方向一次性结算，**O(1)**，无需遍历用户
- 详见 [docs/1.md](./1.md) 第 2/5 节、[others/docs/永续合约8小时资金费实现方案.md](../others/docs/永续合约8小时资金费实现方案.md)

### 3.3 三级保证金线：MM / IM / Solid IM

- **MM（维持保证金）**：清算触发线——净值 < MM 即不安全，可被清算
- **IM（初始保证金）**：开仓门槛——开新仓、加仓前必须满足，给波动留缓冲
- **Solid IM**：主资产口径的更严检查——剔除次级抵押品后仍须满足 IM（防用次级资产垫付主资产义务）
- 测试中 BTC-PERP 是 5% IM / 3% MM（20 倍杠杆），ETH-PERP 是 10% / 5%

### 3.4 全仓保证金与清算

- 全仓：一个账户在**所有市场**的仓位合并计算保证金率，一个市场的浮盈可以覆盖另一个市场的浮亏
- 清算 = 强制交易：清算人以**固定折扣**（如标记价 × 99%）接走仓位，差价归清算人；另收保险费给保险账户
- 穿仓（清算后余额仍为负）→ 坏账清零，由**保险账户**兜底
- 详见 [docs/面试题-撮合开仓清算手续费资金费率.md](./面试题-撮合开仓清算手续费资金费率.md) Q4–Q7

### 3.5 EIP-712 签名订单

- 用户用钱包对订单做结构化签名（免 gas、低延迟），签名覆盖全部字段（价格、数量、费率、过期时间、nonce）防篡改
- 防重放：链上维护"订单哈希 → 累计已成交数量"，支持部分成交，总量不超订单量；后端 **orderId 直接取订单的 EIP-712 digest**，与链上 key 天然对齐
- 支持授权操作员签名 + ERC-1271 合约钱包
- 钱包端 `signTypedData` 示例见 [test/impl/ScenarioSignatureTest.sol](../test/impl/ScenarioSignatureTest.sol) 头部注释

### 阶段 2：链上合约精读（2–3 天）⭐ 核心

**目标**：理解合约架构、paper/credit 模型、一笔 trade 的完整调用链（架构图见 2.1）。

建议顺序（从业务模型到系统框架）：

1. **[Perpetual.sol](../src/Perpetual.sol)** —— 单个市场的资产负债表。关键定义：
   - [balance 结构体 :45](../src/Perpetual.sol#L45)：`int128 paper + int128 reducedCredit` 打包进单槽省 gas
   - [balanceOf :104](../src/Perpetual.sol#L104)：`credit = paper × fundingRate + reducedCredit`
   - [trade :140](../src/Perpetual.sol#L140) → [_settle :253](../src/Perpetual.sol#L253)：结算核心——先展开 credit、加减变化量、再**反推** newReducedCredit；paper 从 0 变非 0 是开仓（回调 `Dealer.openPosition`），归 0 是全平（残余 reducedCredit 作为已实现盈亏回调 `Dealer.realizePnl`）
   - [liquidate :180](../src/Perpetual.sol#L180)：含**价格保护**（expectCredit/requestPaper 交叉相乘，防止清算执行价劣于清算者预期）
2. **[src/libraries/](../src/libraries/)** —— 真正的业务逻辑都在库里（合约只做入口和存储）：
   - [Types.sol](../src/libraries/Types.sol)：`State`（全部状态一个 struct）、[Order :97](../src/libraries/Types.sol#L97)（info 字段 256 位打包 makerFee|takerFee|expiration|nonce）、[RiskParams :136](../src/libraries/Types.sol#L136)（含 `markPriceSource` 预言机地址——价格源切换点）
   - [SignedDecimalMath.sol](../src/libraries/SignedDecimalMath.sol)：有符号定点小数乘除（1e18 基数，永续合约数学的地基）
   - [Trading.sol](../src/libraries/Trading.sol)：[_matchOrders :79](../src/libraries/Trading.sol#L79)（以 maker 价成交、费率可负=返佣、手续费归撮合引擎）、[_priceMatchCheck :206](../src/libraries/Trading.sol#L206)（链上价格硬约束，成交价不劣于 taker 签名限价）
   - [Liquidation.sol](../src/libraries/Liquidation.sol)：[getTotalExposure :100](../src/libraries/Liquidation.sol#L100)（全仓风控核心，遍历所有市场合并敞口）、三级安全线 `_isMMSafe/_isIMSafe/_isSolidIMSafe`、[getLiquidationPrice :207](../src/libraries/Liquidation.sol#L207)（反解临界价，返回 0 表示无仓位/绝对安全）、[requestLiquidation :346](../src/libraries/Liquidation.sol#L346)（固定折扣 + 保险费、禁自清算）

### 阶段 4：后端（1–2 天）

**目标**：理解链下部分做什么：扫链、入库、API、撮合、上链。

- 技术栈速览：Go 1.24 + go-zero 框架 + GORM/Supabase Postgres + Redis（硬依赖）+ go-ethereum（ethclient 直连，ABI 内嵌 JSON）
- 先读：[后端数据流：扫链-入库-API.md](../others/backend/docs/后端数据流：扫链-入库-API.md)（全局地图，⚠️ backend/README.md 已过时——描述的是旧 MySQL 方案，以 docs 和代码为准）→ [什么是限价单、市价单.md](../others/backend/docs/什么是限价单、市价单.md) → [撮合数据结构的技术方案.md](../others/backend/docs/撮合数据结构的技术方案.md) → [尝试撮合方案.md](../others/backend/docs/尝试撮合方案.md)
- 代码入口：[metanode.go](../others/backend/metanode.go)（装配全部后台任务）→ `internal/engine/`（撮合/订单簿/资金费/清算）、`internal/listener/`（扫链/行情）、`internal/chain/`（链交互）、`internal/handler/` + `logic/`（API）
- 关键知识点（按数据流学）：
  1. **扫链入库**（[treasurydepositwatcher.go](../others/backend/internal/listener/treasurydepositwatcher.go)）：12s 轮询 USDC `Transfer` 日志（to=Treasury）+ 确认块数安全高度 + **Redis 游标**（挂了回退 DB MAX(block_number)）+ 幂等（UNIQUE(tx_hash, log_index)，写失败不推进游标）
  2. **两种充值路径**：托管充值（转平台收款地址，链下台账）vs 合约入金（调 `Dealer.deposit`，链上保证金）——项目踩过"钱到了但不能交易"的 P0 坑
  3. **撮合引擎**（[matchengine.go](../others/backend/internal/engine/matchengine.go)，最核心 1100+ 行）：
     - 订单语义：**"签名即限价"**，无订单类型字段；隐含限价 = |credit|/|paper|；"市价单" = 参考价 + 滑点容忍算出的签名限价（三道防线：order-preview 模拟 → 签名限价 → 链上 `_priceMatchCheck`）
     - 订单簿（[orderbook.go](../others/backend/internal/engine/orderbook.go)）：价档双向链表 + 同价 FIFO + orderId 索引三层结构，撤单 O(1)、深度 O(N)
     - 双路径撮合：新单作 taker 吃簿 + 100ms 定时交叉撮合；成交价 = Maker 价；禁自成交
     - **orderId = 订单的 EIP-712 digest**，与链上"订单哈希→累计成交量"的 key 天然对齐，防重放
     - **WAL + 崩溃恢复**：所有状态变更先写 `engine_events` 表再进内存，重启回放；这是内存撮合敢用的底气
     - **Redis leader 锁**：Setnx + Lua 原子续租，只有 leader 撮合/上链，standby 轮询事件表同步
  4. **上链提交**（[tradedata.go](../others/backend/internal/chain/tradedata.go)）：批量（≤10 笔/秒）编码 `tradeData = abi.encode(Order[],签名[],成交量[])` 发 `Perpetual.trade`；**nonce 管理**是吞吐关键（同账户连续 nonce 打包进一个区块；串行"发一笔等一笔"只有 12s/笔）
  5. **失败回滚**：链上 revert → `rollbackMatch` 内存恢复 remain 重新挂簿，订单不能标为已成交
  6. **EIP-712 一致性**：后端 [eip712.go](../others/backend/internal/chain/eip712.go) 的域（MetaNode/v1/chainId/Dealer 地址）与 struct hash 必须和合约 [EIP712.sol](../src/libraries/EIP712.sol) 完全一致；签名 V 值支持 0/1、27/28、EIP-155 三种格式归一化
- 已知问题（读代码时注意）：Liquidator 未实现（链上不会自动清算）；sqlx 侧表未建（positions/withdraws 等查询会报"表不存在"）；CORS/WS CheckOrigin 全开；撮合私钥明文在 yaml（勿提交 Git）；后端是常驻进程不能部署到 Vercel（见 [DEPLOY.md](../others/backend/docs/DEPLOY.md)）
- 检验：能讲清"一笔签名订单从 POST /api/v1/orders 到链上 trade 成功"的每一步；能指出哪里可能出"假成交"

## 7. 常见坑与经验

来自项目真实踩坑记录（todo.md 已知 Gap + 面试题文档 + 代码现状）：

1. **托管充值 ≠ 链上保证金**：用户转到平台收款地址只是链下台账入账，必须再调 `Dealer.deposit` 才能交易。充值产品必须有两个入口且文案区分（P0 踩坑）
2. **链上 revert 与链下状态不一致**：撮合成功后 `trade()` revert 时，DB 里订单不能标为已成交，否则订单簿"假成交"（P2 Gap）
3. **nonce 串行提交是吞吐瓶颈**：同账户"发一笔、等收据、再发下一笔"= 每块一笔（12s/笔）；连续 nonce 应打包同批进 mempool
4. **mark/index 价格口径必须统一**：测试网 mark=30000e6 与 Oracle 1e18 口径差 12 个数量级，资金费会失真（资金费方案文档里的最高优先级风险）
5. **合约大小超限**：MetaNodeDealer 拆分多文件 + Sepolia profile 开 via_ir 才能压到 24KB（EIP-170）以内
6. **EIP-712 域/结构不一致**：后端与合约两处任何一个字段名、类型、顺序不同，验签必失败——用 ScenarioSignatureTest 对齐
7. **后端 README 已过时**：描述的还是旧 MySQL 方案；以 docs/后端数据流：扫链-入库-API.md 和代码为准
8. **自动清算未实现**：liquidator.go 是占位，链上不会自动清算；sqlx 侧表（positions/withdraws 等）未建表，查询会报"表不存在"
9. **双 ORM 并存**：go-zero sqlx 的 `?` 占位符与 pgx 不兼容，部分表必须走 GORM（历史遗留，新手易踩）
10. **安全配置勿忘**：撮合/资金费私钥明文在 yaml（勿提交 Git）、CORS/WS CheckOrigin 全开（生产收紧）、Redis 是硬依赖、后端是常驻进程不能部署到 Vercel
